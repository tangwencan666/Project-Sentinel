# Interview Q&A — 49 evidence-based questions

## 1. 为什么做这个项目？

希望验证大模型能否通过工具完成可复查的工程调查，而不只是解释一段报错。事故调查天然涉及跨日志、指标、调用链、源码和基础设施的证据关联，也能用可复现故障检查结论。

## 2. 为什么不用普通监控规则？

监控规则非常适合发现已知模式，项目中 Rule 在固定八场景里达到 7/8。Agent 的研究目标是组合异构证据、关联源码、产生可检验假设和候选；目前结果没有证明它全面优于规则。

## 3. 为什么 Rule 7/8 (87.5%)，V1 只有 5/8 (62.5%)？

Rule 编码了本基准的领域判据，问题空间有限。V1 需要自己规划、选工具和推理，既可能错误归因，也会付出更多调用成本。这不是可以泛化到所有生产事故的模型排行榜。

## 4. Hybrid 是什么？

确定性 Triage 提供观测信号和约束，模型负责调查与解释；Runtime 负责工具权限、预算、状态和提交校验。模型不直接读 Scenario Registry 的答案，也不直接执行任意 shell。

## 5. V3 为什么失败？

上下文重建没有可靠恢复工具错误、验证反馈和未完成要求；收敛策略又提前关闭补证据工具。结合截断、结构化恢复和预算问题，八次只完成两次。低 token 包含提前失败，不能宣传为优化成功。

## 6. V3.1 修复后为什么也只有 1/8？

首轮修复仍暴露 completion budget、消息大小和总时限问题。该 1/8 没有被后续覆盖；单独资格验证逐步达到 5/5 后才进入 V4。资格测试不进入正式准确率分母。

## 7. Agent Runtime 是什么？

它是控制执行的工程层：状态机、预算、工具调用、错误反馈、证据引用、结构化校验、检查点和恢复。这里使用自建 Python Runtime，不把对话历史当成唯一状态。

## 8. Tool Calling 怎么实现？

提供明确的工具 schema，解析模型的工具调用参数，经本地校验与 allowlist 后交给 dispatcher。结果与 ToolError、Evidence ID 进入持久账本，再返回模型；原始工具参数不是任意可执行代码。

## 9. 如何避免 Ground Truth Leakage？

Scenario Registry、评分器和实验答案不在 Investigator 可读工具路径内，DB 调查角色不能读评估表。最终仍发现 generic fault helper 可读，暴露实验实现线索；所以只能说隔离了真值接口，不能说完全盲测。

## 10. Evidence 怎么管理？

每条证据有 ID、run_id、incident_id、来源工具、收集时间和原始 payload。提交引用必须属于本次 Run 且实际读过；录制导出验证同一个 Run，不把其他场景的漂亮结果拼进去。

## 11. 为什么需要 Critic？

它检查因果链、替代解释、测试充分性和回归风险，结构校验同时检查引用与实际测试。Critic 能降低草率接受的风险，但仍是模型，不是外部事实裁判。

## 12. Critic 为什么会错？

与 Investigator 使用同模型可能存在相关错误；提供给 Critic 的证据也可能不完整。最终重试风暴案例中，它的压缩包漏了一条已经引用的代码证据。全部八场只得到 PARTIALLY_VERIFIED，不能说验证问题解决了。

## 13. 为什么要 1.46M tokens？

这是八场完整工作流的累计值，包含规划、多轮工具结果、代码、假设、修复与复核，106 次真实模型调用。输入 1,422,496，输出 39,374；不包含 Evaluator，包含评分则为 1,592,980。

## 14. 怎么降低 token？

优先减少重复工具查询、复用已提交响应、改进结构化证据选择及详情按需读取。需要同时观测完成率、正确率和遗漏证据，不能再次只优化压缩比例。Phase 5 没有为刷分重跑模型。

## 15. 为什么不用 RAG？

当前主要对象是事故发生时的动态遥测和小型受限代码库，用工具读取和 AST 索引即可直接定位。大规模 runbook/文档检索可能适合 RAG，但本项目没有把向量数据库作为已经实现的能力。

## 16. 为什么不用 LangChain / LangGraph？

项目选择直接实现 Python 状态和调用协议，以便精确记录恢复、预算和引用行为。并非认为框架无用；如果改用图框架，仍需保留业务状态、工具权限和真实评估，不能假定框架会自动解决可靠性。

## 17. Checkpoint 怎么恢复？

保存 phase、假设、P0 错误、关键证据、未完成动作、预算和 provider 状态。实际杀死 Runtime 并重启后按同一 run 继续；响应 journal 和工具回执避免重复处理已提交结果。

## 18. 能保证 exactly-once 吗？

不能。响应和费用元数据提交后可复用，但远端已经处理、进程还没持久化就崩溃，可能重发请求并重复计费。目前也没有分布式 worker 执行租约。

## 19. 如何防 Prompt Injection？

把日志、代码注释、Trace 和描述视为不可信数据；真正边界是工具 allowlist、参数校验、路径权限、受限 Patch AST 和无秘密的候选进程。四项真实模型探测通过只证明那些样本，没有普遍保证。

## 20. AI Patch 怎么防危险修改？

只支持指定业务函数、保持签名、限制单文件 diff 与 AST，不允许任意导入、属性访问和任意调用；真值、评分器、测试和 secret 路径不可改。候选再通过不变合同与真实依赖重放。

## 21. 为什么不能直接上线 Patch？

有限测试覆盖不了全部输入、并发和生产条件，财务逻辑风险尤其高。项目通用候选是 review-only；HTTP 500 演示即使测试通过，也没有部署。停止故障注入不能冒充代码修复。

## 22. Kafka 故障怎么查？

比较分区 end offset、committed offset、lag 和窗口生产/消费速率，再结合消费者日志与生命周期。HTTP health 正常不保证消费者工作；项目曾因此得到混杂试验，后来加入消费者就绪和进度检查。

## 23. Redis 故障怎么查？

查看目录 key TTL、命中/未命中、内存和逐窗口变化，同时交叉验证 DB 查询增长与 Trace。全局累积 miss rate 不能直接证明某个 key 是根因，模型需要说明这种限制。

## 24. Trace 怎么使用？

定位错误 span、慢路径、服务扇出和重复调用，再与日志和指标关联。详情工具保留原始 span 对象。一次采样没有出现某条边，不等于系统不存在该依赖。

## 25. PostgreSQL 问题怎么区分？

慢 SQL 看等待事件、query fingerprint、调用数与耗时；连接池耗尽看排队、占用和获取连接超时；N+1 看一次请求内的重复查询。不能只凭数据库存在慢查询就解释所有上游错误。

## 26. 如果换模型会怎么样？

可能改变工具使用、JSON 合规、推理和成本，需要新的版本化实验。当前结论仅来自实际 deepseek-chat 运行，不声称其他模型会复现同样成绩。

## 27. 为什么不用 GPT？

本轮实际配置和冻结比较使用 deepseek-chat，保持模型一致便于研究 Runtime 变化。这不是经过模型横评后的优劣结论，也没有用未运行的数据声称 GPT 更好或更差。

## 28. 项目最大的限制是什么？

单轮八类受控事故，不能证明生产泛化；模型成本高；Critic 证据交接仍有缺陷；实验 helper 可见。修复引擎只覆盖四类受限函数，沙箱共享内核，不能支持任意恶意仓库。

## 29. 真正上线还缺什么？

多租户鉴权、秘密管理、权限审批、分布式执行租约、配额和费用控制、生产采样与 SLO、独立复核、灰度/回滚及更强执行隔离。公开录制 Demo 的安全范围与 live 生产调查系统不同。

## 30. 为什么重试风暴仍然错？

模型看到约 4.9 倍 payment 调用，却把快速 503 当成 causal origin，把 order 的立即重试视作次要放大。它还推测了未读取的 Redis fault key。该首轮错判原样保留，没有场景特判补分。

## 31. 189 passed 代表什么？

Phase 4 冻结源码的自动化门禁，包含协议、本地 HTTP provider fixture、真实 PostgreSQL/Redis、沙箱和安全边界测试。它不是 189 次云模型评估，也不是 189 个真实生产事故；Phase 5 新增测试另列。

## 32. Demo 是不是 Mock？

不是伪造遥测或预写结论：页面读取真实冻结记录，并明确 RECORDED RUN、时间和 run_id。播放时不会重执行工具；这是一种离线证据展示，而不是实时生产状态。测试中的 mock/fixture 则单独标注。

## 33. 如何证明没有拼接多个 Run？

导出器检查 Incident、Evidence、Tool Call、Patch 的 run_id 与 incident_id 一致，保留事件原 ID/时间/顺序，并记录源文件及公开文件 SHA256。摘要是可复现投影，原始冻结文件不被编辑。

## 34. 公网 Demo 如何禁用危险操作？

使用独立只读镜像，没有 provider/tool/DB 模块、secret 或生产卷；只提供录制数据 API，写方法全部拒绝。`PUBLIC_DEMO_MODE=true`，无检测器和自动恢复。Local Live 使用另一 compose 文件且须显式启用。

## 35. 面试官应该重点看什么？

看工具证据能否支撑根因、错误后是否有界恢复、Patch 是否经过实际验证，以及失败与成本是否诚实呈现。最值得讲的是 V3 失败后沿状态、协议和观测链路定位问题，而不是只展示最终准确率。

## 36. Sentinel 到底解决什么业务问题？

微服务结账失败时，帮助工程师跨日志、指标、调用链和代码调查原因，生成有证据的报告与可测试候选。它面向调查和验证，不声称能无人值守地恢复任意生产事故。

## 37. 为什么需要 AI，Hybrid 为什么提高？

AI 用于组合异构证据、选择下一步工具和关联代码；固定模式可由规则更便宜地处理。V2 将确定性 Triage 与约束加入流程，根因从 V1 的 5/8 到 6/8；八个样本不足以把每项改动的贡献单独归因，也没有证明普遍优于纯规则。

## 38. V4.1 究竟修了什么？

后续 Runtime 加强显式状态重建、错误保留、消息预算、结构化修复、引用可读记录、检查点与证据整理，并修复实验环境就绪问题。最终工作流 8/8、根因 7/8，但可读源码与队列也变化，不能称为纯上下文压缩带来的因果提升。

## 39. Metrics 和 Logs 有什么区别？

Metrics 用聚合窗口说明“哪个服务、何时、错误率或延迟怎样变化”；Logs 给单个事件的状态码、异常与 trace_id。Trace 再连接一次请求经过的服务；三者相互验证，单一高错误率不能直接证明源码根因。

## 40. 连接池耗尽怎么查？

看可用连接、等待请求、连接获取超时以及占用趋势，再查 PostgreSQL 会话、等待事件和请求 Trace。连接池排队与数据库全局连接上限不是一回事；要定位哪个服务在等待以及连接为什么长期占用。

## 41. N+1 Query 怎么发现？

在同一请求 Trace 中检查一个集合查询之后重复执行的相似 SELECT，与数据库调用数、语句指纹和代码循环交叉验证。本实验的受控模式是一条 ID 查询后四十次逐商品查询；调查 Agent 必须从证据得出，而非读取真值注册表。

## 42. 为什么 token 主要花在 Input？

工具描述、已有状态、日志/Trace/源码和证据在多轮模型请求中反复进入输入。V4.1 input 1,422,496、output 39,374，共 1,461,870；不是一次 Prompt，也不是用户打了这么多字。需要按调用检查重复内容和遗漏风险，不能只降低输出上限。

## 43. Structured Output 为什么失败？

合法 JSON 也可能字段缺失、类型错误、文本过长、枚举无效或引用未读证据；截断与协议异常又是不同类别。必须记录原调用、finish/预算状态和具体校验错误，不能把所有失败统称为 DeepSeek JSON 问题。

## 44. Schema Repair 为什么必要？

校验失败后，给模型明确字段约束与错误反馈，在预算内修复原提交；同时保留原错误。它不能替模型编造正确结论，也不能在关键状态根本没交付时无限重试。

## 45. Circuit Breaker 解决什么？

模型可能反复使用同样错误的工具或参数，消耗预算且没有新证据。重复失败达到阈值后停止同类循环、给出显式失败状态；这提高可控性，不保证根因一定正确。

## 46. 如何防 Shell Injection？

调查不暴露任意 Shell Tool；补丁只进入受限文件/AST 与固定验证流程，进程参数按数组传递，不把模型文本拼进 shell 命令。公开镜像不含工具执行模块。受限执行仍共享内核，不能因此称为完全隔离。

## 47. API Key 如何保护？

凭据保留在本地被忽略的 `.env`/只读 provider 配置挂载；日志与导出做脱敏，前端与公开镜像不接收 Key。发布前扫描配置值、Token 形态和 ZIP/Git 历史；扫描有范围限制，不能证明所有编码形式的秘密都被发现。

## 48. AI Patch 是如何生成与验证的？

模型基于当前 Run 的源码与证据提交真实 diff；路径、函数签名、AST 和风险检查后，固定合同测试比较基线与候选，再执行专用 PostgreSQL schema、Redis namespace、Kafka topic 下的三服务重放。演示 pricing 是九项测试通过、八个请求恢复，但候选未部署。

## 49. 为什么必须有 Fault Lab？

只有异常日志，没有已知受控原因，就很难评估 Agent 是否真的定位正确。Fault Lab 提供可触发、停止和复现的真实故障及隔离真值；但故障由作者设计，也限制了外部有效性，不能替代独立真实事故验证。
