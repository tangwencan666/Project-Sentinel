# V3.1 首轮及后续问题：中文导读

[文档导航](index.md) · [英文原始记录](phase4-followup-findings.md)

本记录的问题登记在首轮八场完成后；首轮运行中没有修改冻结 Runtime 或 Prompt。

1. 固定错误不保证阶段推进。连接池和 N+1 已有假设却没有提交，缓存场景甚至没有建立假设；应显式控制补证/假设/提交进度并保留纠错能力，而非加大工具上限。
2. 脱敏序列化反复读取配置。一个 N+1 Checkpoint 的 `settings()` 遍历 3,423 次；独立只读诊断用内存快照测得 31 ms。后续成对测量口径另见 Runtime 记录，不能将不同探测数字混用为整体提速。
3. 读取登记需发生在实际模型输入边界。工具成功后若结果被上下文淘汰，不能算已交付；应验证组合路径而不只测 detail 适配器。
4. Provider parse 状态要与 Checkpoint 同步。修复响应不能覆盖原响应的无效参数诊断，同批成功兄弟参数也不能抹除早先错误；运维错误不是 JSON 错误。
5. 嵌套 JSON 消息信封需按真实序列化预算。78k 内部上下文检查不代表完整 messages 小于 Provider 90k 限制；固定状态装不下时应明确失败。

3.1.1 的 N+1 原输出与两次修复均 `finish_reason=length`、2,500 输出 Token，属于确认截断。改用紧凑字段和真实 signal ID，而非提高输出上限；Jaeger 超时和健康窗口中断作为模型调用前的操作中断单独保留。

3.1.2 避免截断后，450 字符摘要等 schema 错误却消耗提交次数，预算错误掩盖原 schema 失败。应将无效结构计入纠错预算，只有有效语义提交占提交额度，原三次上限不变。字段描述还需恢复“未解决反证”与“已排除替代解释”的区别，不能自动删反证制造结论。

后续资格工件使用新名称，排除冻结首轮比较；V4 若继承这些修复，必须说明不是纯压缩消融。
