| 问题 | 修复或限制 |

| P1-01：冻结 Critic 8/8 输入缺根因必需引用 | 必需 ID 先于去重/来源上限；缺失或超限明确失败；Critic 只引用实际交付集合。离线重打包六场完整、N+1/慢查询两场超过 14,000 字符，不是当前 8/8 效果验证 |

P3 包括八场、同模型评分、缺重复/消融的外部效度限制；多代路径共存的维护成本；同步 JSON、有限 LRU 和编译器重复遍历的容量边界。没有据此虚构生产吞吐或负载结果。

## 事实与来源

六服务使用不同进程但共享 `services/app.py` 与数据库；完整 Lab 14 个 Compose 服务，默认公开模式一个。PostgreSQL、Redis、Redpanda/Kafka 和 OTel 都有真实数据链。25 个注册工具不等于当前 Investigator 可见的 18 个。

调查器无任意 shell、SQL、HTTP、文件或环境权限；源码限制、跨 run 引用、参数绑定与 Pydantic 契约有效。可读 `runtime.fault()` 暴露实验管线，不能声称完全无实验线索。进程、角色、基础设施共享意味着能力限制不抵御主机管理员或任意服务器 RCE。

八场 V4.1 的工作流 8/8、根因/服务 7/8、Token 1,461,870 均与账本重算一致；Evaluator 另 131,110，合计 1,592,980。所有 Critic 仍为 `PARTIALLY_VERIFIED`，重试风暴错答不变。V2/V3 有首个有效 pool 选择，V4 有混杂，V4.1 可读业务源码变化，因此不是同条件单变量消融。

定价候选由同 run 真实模型源码产生，通过九项合同和八输入 HTTP 重放，但没有部署。204 事件、19 证据与候选属于同一 run。哈希来源是内部可核验记录，不是 Provider 签名或外部独立人工重评。
