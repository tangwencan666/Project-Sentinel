# 3 分钟项目介绍

## 0:00–0:40 · 从业务问题开始

“用户结账失败可能是支付超时、库存查询太慢，也可能只是代码对空值处理不当。Sentinel 要解决的是：让事故调查有可复查的依据，而不是让聊天机器人猜一个原因。我搭了六个电商微服务，真实执行 HTTP、SQL、缓存与消息操作。”

## 0:40–1:20 · 调查怎么发生

“Fault Lab 能触发和停止八类故障。Hybrid Agent 先用确定性 Triage 收集异常信号，再由模型规划查询。Tool Calling 只能调用登记过的日志、指标、Trace、数据库和源码工具。每个结果成为带 run_id 和时间的 Evidence；结论必须引用本次调查实际读取的证据。实验答案留给评分器，调查工具不能直接读取，但代码 helper 仍暴露部分实验线索。”

## 1:20–2:00 · 展示修复边界

“录制案例是结账 HTTP 500。模型读到日志里的 TypeError 和 pricing 源码，生成处理 None discount 的两行候选。原合同测试有两项失败，候选九项通过；同样八个故障输入在三个 HTTP 服务和真实依赖中从全部失败变为全部成功。它仍是高风险候选，没有部署，Critic 也只给了部分验证。”

## 2:00–2:40 · 失败带来的工程工作

“V2 的八次流程能完成，但 token 很高。我在 V3 压缩上下文，结果只有 2/8 完成。定位后发现错误反馈丢失、收敛过早和结构化输出恢复等问题。后续把状态、预算、证据引用和检查点做成显式 Runtime，测试真实进程崩溃后的恢复。V3.1 首轮仍失败，记录没有被覆盖。”

## 2:40–3:00 · 结果与限制

“最终 V4.1 完成 8/8，根因与服务定位各 7/8；重试风暴仍错，用量约 146 万 tokens。我没有把它刷到满分，也不能说它优于所有规则或能直接进生产。面试展示使用冻结的真实回放，支持检查工具、证据、测试和失败记录。”
