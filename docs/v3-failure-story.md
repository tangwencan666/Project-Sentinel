# V3 失败故事 · STAR 与工程复盘

## Situation

V2 Hybrid 的八次工作流全部完成，根因 6/8 (75.0%)，但消耗 1,531,642 tokens。上下文里反复带入工具结果，调查成本偏高。

## Task

目标是在保持证据、错误反馈与完成能力的前提下降低上下文成本，而不是单独追求更短 Prompt。

## Action

V3 尝试压缩和分层重建上下文，用摘要替代大段原始证据，并调整调查收敛。保留首轮调用账本，分别观察工具、结构化输出、预算与终止原因。

## Result

V3 工作流降至 2/8，根因仅 1/8 (12.5%)，tokens 为 896,380。提前失败也会少花 token，所以不能称为成本优化成功。页面标记 FAILED EXPERIMENT / RUNTIME RELIABILITY FAILURE。

## Investigation

从调用记录与源码交叉检查：上下文重建遗漏工具错误和校验反馈；收敛阶段过早关闭补证据工具；structured output、消息大小、completion budget 和总时限共同限制了继续调查。不能简单归咎为“DeepSeek 不会 JSON”或一个 token 参数。

第一次 V3.1 干预仍只有 1/8 工作流，失败继续保留。之后单独资格验证达到 5/5，不能拿它替换首轮 1/8 或计入正式准确率。

## Fix

显式 Runtime 状态保存关键错误、证据、假设和未完成动作；Context Reconstruction 恢复这些约束；分开预算并记录终止原因；Schema Repair 提供有界校验反馈；Checkpoint 与已提交响应/工具回执支持恢复。Evidence Compiler 将原始观测转为带来源、遗漏说明和详情入口的结构，而不删除原始 payload。

这不是“摘要永不丢信息”：最终仍发现 Critic 漏传一条根因引用证据，也没有端到端 exactly-once 计费。

## Final

最终独立 V4.1 队列为 8/8 工作流、根因与服务定位各 7/8 (87.5%)，仍花费 1,461,870 workflow tokens。Runtime、源码可读范围与环境发生变化，不能把结果包装成纯压缩消融。重试风暴仍错，所有首次失败保留。

**面试落点：**我学到的是要把上下文、状态与协议当作可测的执行系统；比“模型最后答对了”更重要的是能解释为什么失败、证据在哪里、下一次能否恢复。
